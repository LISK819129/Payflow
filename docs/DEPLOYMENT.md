# Deploying PayFlow (Render)

PayFlow runs as three pieces: a **web service** (Next.js app, API, MCP server, PayPal webhook receiver), a **background worker** (pg-boss jobs: workflow steps, PayPal event routing, timers, observations) and **PostgreSQL**. PayPal stays in **Sandbox**; PayFlow refuses to boot with `PAYPAL_ENV=live`.

`render.yaml` is a Blueprint for exactly this. It contains no secrets.

## Services

| Service | Render plan ID (legacy name) | Build | Start |
|---|---|---|---|
| `payflow-web` | `0.5c-512mb` (Starter), **1 instance** | `corepack enable && pnpm install --frozen-lockfile && pnpm build` | `pnpm start` |
| `payflow-worker` | `0.5c-512mb` (Starter) — background workers have no free plan | `corepack enable && pnpm install --frozen-lockfile` | `pnpm worker` |
| `payflow-db` | `0.1c-256mb` (Basic-256mb), PostgreSQL 18, 1 GB disk | — | — |

Why not the free tier: background workers have no free plan; a free web service sleeps after 15 minutes without traffic (slow first load for judges, late webhooks); free Postgres expires after 30 days.

- **Node** 24 (`NODE_VERSION=24`). **pnpm** 11.15.1 via `packageManager` + corepack. `NODE_ENV` is *not* set on the web service: Render sets it to `production` at runtime, and setting it at build time would make pnpm skip the dev dependencies `next build` needs.
- **Pre-deploy** (web): `pnpm db:migrate && pnpm db:seed` — both idempotent. Migrate refuses a non-UTF8 database, applies the Drizzle migrations and creates the pg-boss queues; seed creates the judge owner if missing.
- **Health**: `GET /api/health` (liveness) and `GET /api/health/ready` (readiness: database reachable, migrations current; also which integrations are configured and whether a worker heartbeat is recent — states only). Render's health check uses `/api/health/ready`.
- **Deploys** are manual (`autoDeployTrigger: "off"`): a push to `main` does not redeploy the judging environment by itself.
- **One web instance.** Rate limits (login, MCP, AI drafting, Test Runs) are in-process — safe with exactly one instance. Scaling out would need them moved to Postgres first. The money guards (AI caps, authority, budgets, idempotency) are in Postgres already.

## Environment

Entered once in the Render Dashboard when the Blueprint is created (`sync: false`): `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `OPENAI_API_KEY` (on **both** web and worker, same values), and on the web service `SEED_OWNER_EMAIL`, `SEED_OWNER_PASSWORD`. Everything else is in `render.yaml`.

| Variable | Notes |
|---|---|
| `DATABASE_URL` | From the Render database (`fromDatabase`) — a new credential, never the local-development password; PayFlow refuses to boot in production if it is reused, if the host is local, or if the password is shorter than 16 characters. |
| `APP_URL` | Not set: defaults to Render's `RENDER_EXTERNAL_URL` (`https://<service>.onrender.com`). Must be https on the web service; the worker serves no URLs. |
| `SESSION_SECRET` | Generated by Render (256-bit) per service. Only the web service uses it. |
| `PAYPAL_ENV` | `sandbox` (the only accepted value). |
| `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET` | The existing PixelForge US Sandbox app. |
| `PAYPAL_WEBHOOK_ID` | `9MJ408823R309725D` — the existing Sandbox webhook. Moving it to the Render URL keeps its id. |
| `PAYPAL_ALLOW_SIMULATOR_EVENTS` | `false`. |
| `AI_PROVIDER`, `OPENAI_API_KEY` | `openai` and the key. Never exposed to agents or the browser. |
| `AI_BUDGET_USD` | Lifetime hard cap on this database (5). |
| `AI_DAILY_CAP_USD` | Rolling 24-hour cap (1). Required when `PAYFLOW_DEMO_MODE=true` and AI is on. |
| `AI_COMPILES_PER_USER_PER_HOUR`, `AI_COMPILES_PER_WORKSPACE_PER_DAY`, `TEST_RUNS_PER_USER_PER_HOUR` | 12 / 60 / 60. |
| `PAYFLOW_DEMO_MODE` | `true`: the owner's "Restore demo setup" in Settings. |
| `SEED_OWNER_EMAIL`, `SEED_OWNER_PASSWORD` | The judge login. A new strong password; share it privately. |
| `DEMO_SUPPLIER_ACME_EMAIL`, `DEMO_SUPPLIER_AWS_EMAIL` | The two Sandbox personal accounts used as demo suppliers; added after the first deploy. |
| `TRUSTED_PROXY_HOPS` | 1 (Render's proxy): how the caller's IP is read from `X-Forwarded-For`. |
| `PAYFLOW_WORKER_WATCH` | `0` on the worker. |

Never set `PAYFLOW_ALLOW_LOCAL_DB` on a host — it exists only for a local production rehearsal.

## First deploy

1. Render Dashboard → **New → Blueprint** → repository `LISK819129/Payflow`, branch `main`. Check it lists exactly `payflow-db`, `payflow-web`, `payflow-worker` with the plans above; enter the `sync: false` values; **Apply**.
2. The web pre-deploy step migrates the empty database and creates the judge owner.
3. Sign in as the judge owner → **Settings → Restore demo setup**: creates the demo workflows, authorities and the Cloud Procurement Agent; its credential is shown once.
4. Move the PayPal webhook (next section).
5. Check `https://<host>/api/health/ready` → `"status":"ready"` with `"worker":"recent"`.

## Moving the PayPal webhook

The Sandbox app has one PayFlow webhook (currently pointing at a stopped development tunnel). From any machine with the Sandbox credentials:

```
pnpm paypal:webhook:register https://<render-host>
```

It **moves** the existing webhook (`PATCH`), removes other PayFlow webhooks pointing at dead tunnels, and only creates one if none exists — never a duplicate. Webhooks for other apps are not touched. It prints `PAYPAL_WEBHOOK_ID`. Incoming events stay signature-verified, stored once per PayPal event id, confirmed with PayPal's API before they confirm anything, and processed asynchronously by the worker.

## Demo Sandbox recipients

Phase 9's payouts ended `UNCLAIMED` because the recipient addresses were not PayPal accounts. For the final demo, create two **Sandbox personal accounts** (developer.paypal.com → Testing tools → Sandbox accounts → Create account → Personal, US), e.g. "Acme Cloud" and "AWS", and set their generated emails in `DEMO_SUPPLIER_ACME_EMAIL` / `DEMO_SUPPLIER_AWS_EMAIL`, then press **Settings → Restore demo setup** (or `pnpm demo:restore` locally) — it updates the demo authority's allow-list as a new, audited version. A payout to a real Sandbox account is reported by PayPal as `SUCCESS` for the item, which PayFlow shows as **Settled**. Creating Sandbox accounts needs a person logged in to the PayPal developer dashboard; PayFlow does not do it.

## Local production rehearsal

```
# a fresh UTF8 database on the embedded Postgres, then:
# .env.production.local (git-ignored): DATABASE_URL=<judge db>, PAYFLOW_ALLOW_LOCAL_DB=true, APP_URL=http://localhost:3000, PAYFLOW_DEMO_MODE=true, AI_DAILY_CAP_USD=...
pnpm db:migrate && pnpm db:seed && pnpm demo:restore   # with DATABASE_URL pointing at the judge db
pnpm build && pnpm start
NODE_ENV=production PAYFLOW_WORKER_WATCH=0 pnpm worker
```
